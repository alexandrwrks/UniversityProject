# Object Oriented Practics

Учебное приложение на C# / .NET 10 и Windows Forms. В одном проекте реализованы обязательные требования лабораторных №1–4; каждая работа развивает предыдущую.

## Запуск

Откройте `UniversityProject.csproj` в Visual Studio с установленной поддержкой .NET 10 и Windows Forms либо выполните:

```powershell
dotnet run --project UniversityProject.csproj
```

## Работа с приложением

- На вкладках Items и Customers нажмите Add: появится новая запись, выбранная для редактирования.
- Поля справа показывают выбранную запись. Изменения сразу сохраняются в объекте; отдельная кнопка сохранения не нужна.
- Remove удаляет выбранную запись. Без выбранной записи редакторы отключены.
- Id создаётся автоматически и доступен только для чтения. Товары и покупатели имеют отдельные последовательности: 1, 2, 3… После удаления Id не перенумеровываются. После перезапуска отсчёт начинается заново, поскольку данные не сохраняются.
- Некорректное поле подсвечивается розовым; наведите на значок ошибки, чтобы увидеть причину. В модели остаётся последнее корректное значение этого поля.
- Стоимость вводится в числовом формате текущих региональных настроек Windows, от 0 до 100000 включительно.
- Почтовый индекс: число от 100000 до 999999. Пустой адрес начинается с допустимого индекса 100000; остальные составляющие пустые, пока пользователь их не заполнит. ТЗ задаёт ограничения длины, но не требует непустых строк.

Данные хранятся в памяти до закрытия приложения. Генераторы случайных записей и сохранение в файл относятся к дополнительным заданиям первой лабораторной и в текущую реализацию не включены.

## Что реализовано

Лабораторная №1: классы Item и Customer, закрытые поля и проверяемые свойства, readonly Id, статический IdGenerator с отдельными счётчиками товаров и покупателей, статический ValueValidator, выбор/добавление/удаление/редактирование записей, обработка неверного ввода, заголовок окна, документация классов.

Лабораторная №2: Category с семью категориями и выбором в ItemsTab; Address с шестью проверяемыми составляющими и двумя конструкторами; отдельный AddressControl; Customer.Address типа Address; Store с List<Item> и List<Customer>; передача тех же списков из MainForm во вкладки через открытые свойства.

Исходные имена моделей Items и Customers заменены на Item и Customer согласно ТЗ. Неиспользуемые ItemServices и CustomerServices удалены: вкладки используют коллекции Store напрямую.

## Лабораторная №3 — агрегация

Ветка: `Tasks/3_agregation` (написание из задания). Создана от `Tasks/2_composition`: ветки develop в этом репозитории нет.

- `Cart` хранит список ссылок на товары и вычисляет Amount циклом. Пустой список и присваивание null дают сумму 0.
- У каждого Customer при создании появляются отдельные Cart и List<Order>.
- `Order` получает уникальный Id из отдельной последовательности с 1, время создания, адрес доставки, товары и статус New. Id и время доступны только для чтения.
- Список заказа создаётся отдельно от списка корзины; сами товары сохраняются по ссылке. Поэтому очистка корзины не очищает заказ, а изменение цены товара отражается в суммах связанных корзин и заказов.
- Адрес заказа копируется при оформлении: последующее редактирование адреса покупателя не меняет уже оформленный заказ.

### Пользовательский сценарий

1. На Items добавьте товары и задайте цены; на Customers добавьте покупателей.
2. Перейдите в Carts, выберите покупателя в Customer и товар слева. Add To Cart добавляет одно вхождение; повторное добавление допустимо.
3. Remove Item удаляет одно выбранное вхождение. Clear Cart очищает корзину. Сумма пересчитывается автоматически.
4. Create Order оформляет заказ и очищает корзину выбранного покупателя. Кнопка недоступна без покупателя или при пустой корзине.
5. В Orders выберите строку таблицы. Справа отображаются Id, дата, статус, адрес, товары и сумма. Менять можно только Status; остальные данные доступны для просмотра.

Carts и Orders обновляются из MainForm при переходе на соответствующую вкладку. Сохраняющийся в данных выбор сохраняется по ссылке на объект. После удаления покупателя его выбор сбрасывается. Удаление товара из каталога не уничтожает его в уже созданных корзинах и заказах.

В `doc/ObjectOrientedPractics` добавлены `Practics3.drawio` и `Practics3.png`. Белые ромбы обозначают агрегацию товаров, чёрные — композицию, связи подписаны кратностями.

Дополнительные задания №3 (случайные заказы, отдельный OrderControl, сериализация Store, история статусов, поиск и сортировка) не включены. Данные по-прежнему хранятся до закрытия приложения. Таблица не редактируется и не сортируется, как предписано в обязательной части ТЗ.

Проверки третьей лабораторной находятся в `tests/Verification/Lab3Checks.cs`. Скриншоты проверочной отрисовки сохраняются в `tmp/lab3`; высокие Id в них связаны с созданием объектов в тестах, а не с начальным значением счётчика при обычном запуске.

## Лабораторная №4 — наследование

Ветка: `Tasks/4_inheritance`, создана от завершённой `Tasks/3_agregation`. Ветки develop в репозитории нет; создание и слияние с отсутствующей develop не выполнялись.

`PriorityOrder` наследует `Order`, сохраняет его Id, время создания, статус, адрес и товары, добавляя только DeliveryDate и DeliveryTime. Базовый конструктор вызывается через `base(...)`. Id обычных и приоритетных заказов выдаются из одной последовательности заказов.

У каждого Customer появился IsPriority (по умолчанию false). Флажок Is Priority на Customers меняет этот признак только у выбранного покупателя. Create Order на Carts создаёт PriorityOrder для приоритетного покупателя и Order для обычного. Оба типа хранятся в существующем List<Order>.

### Как проверить

1. Создайте товар с ценой и покупателя.
2. На Customers включите Is Priority.
3. На Carts выберите покупателя, добавьте товар и нажмите Create Order.
4. На Orders выберите заказ: справа появится Priority Options с выбором Delivery Time и Delivery Date.
5. Выберите один из шести интервалов и желаемую дату. Изменения сохраняются сразу в PriorityOrder.
6. При выборе обычного заказа панель Priority Options скрыта. Статус, товары, адрес и сумма продолжают отображаться общим кодом OrdersTab.

Интервалы: 9:00–11:00, 11:00–13:00, 13:00–15:00, 15:00–17:00, 17:00–19:00, 19:00–21:00. Ввод произвольного интервала запрещён и интерфейсом, и моделью. По умолчанию заказ получает сегодняшнюю дату и первый интервал. Смена IsPriority влияет только на будущие заказы; уже созданные не меняют свой тип.

### Учебный PriorityOrdersTab

Класс учебной вкладки оставлен в исходниках, но не добавлен в итоговое главное окно, как разрешено в ТЗ. Он редактирует один PriorityOrder, позволяет менять адрес, статус, дату и интервал, добавлять случайный товар из переданного каталога и удалять выбранное вхождение. Clear Order создаёт новый объект с новым Id; старый объект не изменяется.

Для защиты можно открыть отдельную демонстрацию (из папки с файлом проекта):

```powershell
dotnet run --project UniversityProject.csproj -- --priority-demo
```

В демонстрационном каталоге есть два учебных товара. Режим не меняет работу и начальные Id обычного запуска приложения.
